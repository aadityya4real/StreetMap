# StreetMap authentication architecture

**Status:** Supabase Auth is the selected provider. Stage 11A.5 implements backend access-token validation, internal identity resolution/provisioning, and reusable middleware. Stage 13 adds extension email/password signup/login with extension-native OTP signup verification, Google PKCE login, extension-owned session persistence, refresh through the Supabase client, and local logout. Real provider login/token compatibility has not been tested from this checkout. There is no website login/session or protected contribution route. No password is stored by StreetMap.

## Provider and rollout decision

Use one Supabase Auth project for the Chrome extension and the future `streetmap.in` website so both clients authenticate the same Supabase user. The extension supports Google OAuth and email/password signup/login. Supabase handles credentials and verification; StreetMap never stores passwords. Email verification and recovery delivery depend on Supabase project settings and mail configuration. Identity linking is not implemented in StreetMap; do not merge local users by email equality. Provider identity resolution remains based on validated `(issuer, subject)`.

The extension uses a user-initiated authorization-code flow with PKCE through Chrome `identity.launchWebAuthFlow`. Its callback is generated by `chrome.identity.getRedirectURL()` and must be registered as an exact Supabase redirect URL for each extension ID. The Supabase JS client stores the PKCE verifier in extension-owned storage and exchanges the returned single-use code. Only one Google flow is allowed at a time. Supabase validates the upstream Google OAuth state before redirecting to the extension; the extension also validates callback origin/path and requires a code before exchange. The Google OAuth redirect URI is Supabase's Auth callback, not the extension callback. The extension contains only public project configuration; Google client secrets, Supabase secret/service-role keys, and website secrets must remain server-side.

The future website should use the same Supabase project through a Go backend-for-frontend. The server handles the OAuth callback, validates the response, and issues an opaque `Secure`, `HttpOnly`, `SameSite=Lax` session cookie. Protect state-changing website requests with CSRF and Origin checks. Keep Supabase refresh credentials server-managed. The website and extension have separate sessions even though they share one Supabase user; signing out from one client should not unexpectedly sign out the other.

## Internal identity mapping

StreetMap uses its own `users.id` UUID as the application identity. Migration `00003_auth_identities.sql` adds:

| Column | Meaning |
| --- | --- |
| `id` | Internal UUID primary key. |
| `user_id` | Required FK to `users.id`, with `ON DELETE RESTRICT`. |
| `issuer` | Required exact issuer of the validated external identity. |
| `subject` | Required subject from that validated identity. |
| `created_at` | Timestamp when the identity mapping was created. |

`(issuer, subject)` is unique, and `user_id` is indexed. This allows multiple external identities to map to one StreetMap account while preventing one external identity from mapping to multiple accounts. The API must resolve this pair only after validating the token. It must never accept a client-supplied internal user UUID or use email equality as identity proof.

`users.email` is nullable after migration `00003`. The generated normalized value and unique index remain, so non-null email addresses remain unique while multiple users may have `NULL`. Existing emails are not changed. StreetMap does not automatically copy provider email into this field. The field is optional contact/profile data, not an authentication key. Existing demo users remain unlinked; migration `00003` creates no identity rows and performs no matching or merging.

## Future email/password linking constraint

When email/password is considered, adding a password to a user who is already authenticated with Google should be an explicit account setting on that same authenticated Supabase account. Never merge StreetMap accounts by email equality alone. Supabase documents automatic identity linking by matching email and marks manual identity linking as beta; verify the configured provider behavior before enabling additional sign-in methods. If a second identity belongs to a different Supabase subject, require an explicitly designed, authenticated recovery/linking process rather than silently merging local users. [Supabase Identity Linking](https://supabase.com/docs/guides/auth/auth-identity-linking)

## Go API validation and authorization plan

The backend foundation accepts only a bearer token on handlers explicitly wrapped with `Handler.Authenticated`. It uses `golang-jwt/jwt/v5` to validate the signature, configured asymmetric algorithm (`RS256`, `ES256`, or `EdDSA`), exact issuer, one configured audience, expiration, issued-at (including configured clock skew), and not-before when present. The configured project URL must be a canonical hosted Supabase origin in the form `https://<project-ref>.supabase.co`; user information, custom domains, arbitrary hosts, query/fragment components, non-root paths, and nonstandard ports are rejected. JWKS requests are built from that origin at `/auth/v1/.well-known/jwks.json`, never from token headers. Redirects are disabled and default TLS certificate verification remains enabled.

JWKS cache reads use a short read lock and never wait for network I/O. A single in-flight refresh is shared by concurrent unknown-key lookups. The existing refresh cooldown bounds retries for arbitrary `kid` values; unknown keys fail closed, and expired keys are not served while refresh fails. Successful refreshes replace the cached key map atomically. The cache duration is bounded (default five minutes, maximum ten). The outbound transport resolves the configured project hostname, rejects loopback, private, link-local, unspecified, multicast, shared-address-space, and known metadata IPs, then dials the validated numeric address while the HTTP request retains its hostname for TLS verification. Proxies are disabled. This pins the DNS answer used for each connection and prevents a DNS response from changing between validation and dialing. The destination policy intentionally accepts only hosted Supabase project domains; a custom Supabase domain would need a separately reviewed explicit allowlist. A system resolver may itself use upstream DNS infrastructure outside this process's control, but the returned destination is checked before dialing. A project signature and algorithm still need validation with actual StreetMap Supabase settings. [Supabase JWT guidance](https://supabase.com/docs/guides/auth/jwts), [Supabase signing keys](https://supabase.com/docs/guides/auth/signing-keys)

The verifier also requires Supabase's `role=authenticated` and `is_anonymous=false` claims as an access-token shape check. These claims do not grant StreetMap roles or permissions. When JWK `key_ops` is present, the signing key must permit only `verify`; omission remains accepted. Key type and algorithm-specific key structure are checked, and malformed, empty, oversized, or duplicate-ID JWKS documents fail closed. JWT errors are returned generically and raw tokens are not logged. This is not a separate cryptographic token-type discriminator; a real project's access-token format must be smoke-tested before rollout. In particular, whether every production access token includes `iat`, `aal`, and `session_id`, and the exact types/semantics of those claims, remain unverified. `iat` is validated if supplied; missing `aal` and `session_id` are not currently rejected pending inspection of a real test-project token. No production token fixture or provider claim shape has been assumed.

Focused Go regressions cover cache refresh coalescing and expiry, DNS destination filtering and address pinning, redirect rejection, JWK `key_ops`, malformed/empty/duplicate/oversized JWKS documents, oversized bearer tokens, malformed claim types, and unreasonable future `iat` values. These are local synthetic tests only and do not establish live Supabase compatibility or production readiness.

After validation, the resolver transactionally looks up exact `(iss, sub)` in `auth_identities`. If absent, it creates a local `users` row with `email=NULL`, a validated provider display name or the fallback `StreetMap member`, then inserts the mapping. It never compares or stores provider email and does not link demo or existing users automatically. Conflict handling makes concurrent first-login requests converge to one mapping and removes the losing transaction's temporary user. The resolver checks the local account status every time and rejects `suspended` and `deleted` users. The middleware puts only the internal StreetMap UUID in request context; future write handlers must derive actor identity there and enforce ownership/state themselves. No current route is wrapped. Health, readiness, and `GET /api/v1/notes` remain anonymous. A valid Supabase identity does not imply moderator privileges.

Authentication settings are optional as a group: with all unset, the current public API starts normally and a future protected wrapper fails closed with `503`. Partial or invalid settings fail startup. The issuer, audience, and signing algorithm must be copied from a real project and token before enabling auth; no production values are checked in or assumed.

## Session and logout policy

The extension stores the Supabase session through a custom adapter backed by `chrome.storage.local`, allowing session persistence across popup close/reopen and browser restart. Before client initialization, storage access is restricted to `TRUSTED_CONTEXTS`; content scripts cannot read it. The auth client exists only in the popup bundle and no token is added to UI state, Maps-page messaging, or the public notes request. The Supabase client refreshes an expiring access token when the popup reads the session or uses its auth client; a closed popup is not a continuously running refresh process. Reopening the popup rehydrates/refreshes the session. Local sign-out clears this extension's stored session only.

Supabase access tokens are short-lived, but its refresh tokens do not expire by default; session lifetime controls are plan-dependent. Decide whether StreetMap accepts provider defaults or needs its own reauthentication/revocation policy before launch. Logout should clear the local client's stored session and use the provider's local-session sign-out semantics; it must not revoke the separate website session by default. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [Chrome storage](https://developer.chrome.com/docs/extensions/reference/api/storage)

The Stage 11A.5 API validates JWTs offline and does not introspect Supabase sessions. A provider-side logout or token revocation therefore does not invalidate an already-issued access token immediately; it remains usable until its expiry unless a future online revocation or local session-version check is added. Local StreetMap account suspension/deletion is enforced immediately because the account row is checked on each authenticated request.

## Extension email signup and verification

Email/password signup calls Supabase `signUp` without `emailRedirectTo`; the extension does not use a browser confirmation redirect. If Supabase returns no session, the account panel stays anonymous and enters a pending-verification state. It asks the user for the code from the confirmation message. The extension verifies it with `auth.verifyOtp({ email, token, type: 'email' })`, then confirms an active, matching session before showing the signed-in account. A missing session after OTP verification is an explicit error and never becomes an authenticated UI state. If signup returns a session, the client checks the current Supabase session before treating signup as authenticated.

Resend uses `auth.resend({ type: 'signup', email })` for the same pending address, without a redirect override. UI feedback is shown only after Supabase returns success. The panel masks the email, applies a local resend cooldown, gives rate-limit errors a longer cooldown, and uses neutral resend copy to avoid exposing whether an arbitrary address has a pending signup. Provider details and raw errors are not shown.

**Manual Supabase dashboard setup remains required:** go to **Authentication → Emails → Confirm signup** and update the confirmation template so it includes `{{ .Token }}` as the code the user enters in StreetMap. For example, include text such as `Your StreetMap verification code is {{ .Token }}.` Do not rely exclusively on `{{ .ConfirmationURL }}` for this extension flow. The repository cannot change the hosted dashboard template. If the template still sends only a confirmation link, users will not receive the OTP expected by this UI. See [Supabase email templates](https://supabase.com/docs/guides/auth/auth-email-templates) and the [verifyOtp reference](https://supabase.com/docs/reference/javascript/auth-verifyotp). Google sign-in remains its separate Chrome `launchWebAuthFlow` OAuth/PKCE path and is not verified with email OTP.

Known limitations: email delivery, OTP expiry, rate limits, and whether a signup address is eligible are controlled by Supabase project configuration. Supabase may intentionally return a non-specific result for duplicate addresses; resend copy therefore avoids confirming account existence. Real email delivery and code verification must still be tested against the configured project after the dashboard template is changed.

## Database lifecycle notes

The existing `notes.author_user_id`, `votes.user_id`, and `reports.reporter_user_id` continue to reference the same internal user UUIDs. Identity mappings do not reassign or merge those rows. User deletion remains restricted by existing ownership records and by the identity FK; account suspension/deactivation is the expected authorization control until retention and deletion policy is finalized.

The identity table is only a mapping structure. It does not store passwords, provider access tokens, refresh tokens, Google profile data, or Supabase credentials. Stage 11A.5 does not change the schema; it consumes migration `00003` and leaves existing ownership references intact.

Email verification and recovery need a reliable, budget-approved delivery plan; Supabase's default hosted email service is restricted and best-effort. [Supabase SMTP guidance](https://supabase.com/docs/guides/auth/auth-smtp)

The existing project URL is documented in the Stage 13 handoff; no anon/publishable key or client secret is checked into this repository. The code derives the exact host permission from `VITE_SUPABASE_URL`; invalid or absent config disables auth without affecting public browsing. Manifest permissions include `identity` for the Chrome OAuth flow and `storage` for the trusted session adapter. The Go dependency and backend validation foundation are present, but live OTP email delivery, Google OAuth, refresh behavior, and Supabase token compatibility remain unverified. No contribution system or protected API route was added.

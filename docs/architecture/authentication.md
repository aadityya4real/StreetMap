# StreetMap authentication architecture (proposal)

**Status:** Stage 5B documentation preflight complete; tenant and runtime smoke tests are outstanding. Authentication is not implemented. The current `users` table contains profile/account fields only and has no credential, identity, or session table. Provider capabilities and pricing below were checked against vendor documentation on 2026-10-30; plan details can change and must be reconfirmed before creating a production tenant.

## Decision

**Recommend Auth0 as StreetMap’s managed OIDC provider**, with one Auth0 tenant/issuer and separate registered clients for the website BFF (Regular Web Application) and Chrome extension (Native application). Register StreetMap’s Go API as a custom API/audience. Both clients use the same Auth0 database connection and therefore authenticate the same Auth0 identities. The backend maps the validated `(iss, sub)` pair to one local `users.id`.

Auth0 is the best fit among the reviewed options because it documents all three required pieces together: hosted database-connection login and account recovery, native authorization-code + PKCE support, and a maintained Go JWT middleware/validator for a custom API. This avoids password storage and avoids requiring the extension to borrow a website cookie. It is a recommendation, not a claim that a tenant, callback, email delivery, or price plan has been configured or tested.

## Shared account identity

- On a verified OIDC identity, locate or create the StreetMap user through an `auth_identities` record with unique `(issuer, subject)` and FK to `users.id`. OIDC `sub` is the stable key; email is mutable profile/contact data, not the primary identity. Never auto-link an existing account on email equality alone; require proof of control of both identities or an authenticated linking flow.
- Store only the minimal profile fields required. Treat provider email as verified only when the provider asserts it and issuer policy allows it. The current normalized unique `users.email` index means a future migration must define provider email changes/collisions before sync behavior is chosen.
- Backend authorization uses the local user UUID. A valid provider identity does not bypass `account_status`; suspended/deleted users cannot mutate.

Use separate environments for development and production and do not share production callbacks with local testing.

Using separate clients in the same tenant with the same enabled database connection gives users one Auth0 database identity across the website and extension. Auth0 documents SSO when apps share the same connection, but silent SSO depends on the Auth0 browser session and browser cookie behavior; whether Chrome's `launchWebAuthFlow` shares a usable session in StreetMap's real setup still needs a tenant/browser test. Identity mapping should use the validated `(iss,sub)` pair; Auth0 `sub` carries its user identifier and is tenant/issuer scoped, so never key StreetMap identity on `sub` alone or mutable email. Public `GET /api/v1/notes` remains anonymous. Website BFF cookie requests and extension Bearer-token requests are separate authentication transports to the same API authorization rules.

## Website flow: same-site backend-for-frontend

For `streetmap.in`, use an Auth0 **Regular Web Application** client and a same-origin Go BFF. The browser navigates to Auth0 Universal Login. The BFF binds `state` and OIDC `nonce` to a short-lived server-side transaction, exchanges the one-use code server-to-server using the web client secret, validates the ID token (issuer, web client audience, signature, expiry and nonce), resolves `(iss,sub)` to the local user, and creates an opaque server-side session. Keep the client secret only in server environment/secret storage. Return only a cookie such as `__Host-streetmap_session=<random-id>; Secure; HttpOnly; SameSite=Lax; Path=/` (no `Domain`). Store a keyed hash of opaque session IDs in a session table, rotate at authentication/privilege changes, expire idle and absolute lifetimes, and revoke on logout, password/security events, suspension, and account deletion.

Web requests to its BFF use the cookie. For cookie-authenticated state changes, also require a CSRF token plus strict `Origin`/`Referer` validation and safe method/content-type handling. SameSite is defense in depth, not the only CSRF control. Web JavaScript never receives an OIDC refresh token or session identifier.

If a separate API origin is eventually required, prefer the website BFF proxying to it. Avoid broad cookie domain sharing and wildcard CORS. A direct cookie API needs exact origins, credential rules, CSRF controls, and a reason to accept the added complexity.

## Chrome extension flow

Create a separate Auth0 **Native application** client for the extension. The extension is a public client and has no client secret. From an explicit sign-in button, use Chrome `identity.launchWebAuthFlow` to navigate to Auth0's `/authorize` endpoint with authorization code + transaction-specific PKCE S256 and `state`; do not `fetch` `/authorize`, which does not support CORS. Use the exact callback returned by `chrome.identity.getRedirectURL()`; Chrome captures a matching `https://<extension-id>.chromiumapp.org/*` redirect and returns the final URL. Auth0 requires an exact callback allowlist match. Establish and pin the extension ID through the Web Store item's public manifest key (private signing key stays secret), then register exact development and production callback URIs as needed; never use wildcard callbacks. Validate final callback origin/path and state, then POST the code and PKCE verifier to Auth0's token endpoint from an extension-owned page. Chrome requires host permission for that cross-origin fetch. Auth0's CORS response for this particular Native-client code exchange is not established by the docs reviewed and must be smoke-tested; add only the exact extension origin to Auth0's relevant CORS allowlist if the test shows it is required. Auth0's Native + `None` setting supports PKCE, but does not by itself prove the full Chrome/Auth0 flow works in StreetMap's tenant.

The toolbar action popup is short-lived and may close while the user completes hosted login. Start auth from a dedicated extension-owned sign-in page/tab opened by a user gesture rather than making an assumed popup lifetime part of the flow. The extension requests the StreetMap API audience so Auth0 issues a JWT access token for the Go API; do not use the ID token as a bearer token. No web session cookie or client secret crosses into the extension.

After sign-in, the extension calls only `https://streetmap.in/api/v1` with a short-lived JWT access token in the `Authorization: Bearer` header. Include the configured API `audience` in the authorization request: Auth0 can otherwise issue an opaque token intended for user-info rather than the custom API. The API validates signature/JWKS, `iss`, exact API `aud`, expiry, allowed algorithm (RS256), and required scope/claims; map validated `iss+sub` to the local user and enforce account status/ownership on every mutation. Auth0’s maintained Go middleware examples use these validations and JWKS caching. Do not accept an ID token as an API access token.

Keep the access token in `chrome.storage.session`, not `local`, `sync`, page storage, or content-script state. Chrome documents session storage as in-memory for the extension and cleared on disable/reload/update/browser restart; this is a useful exposure reduction, not protection against malicious extension code or a compromised browser profile. Initially omit refresh tokens from the extension: when the access token expires, request interactive reauthentication (Auth0 SSO may reduce friction, but do not promise website-to-extension session sharing in Chrome’s auth window). If product evidence later justifies silent renewal, enable Auth0 refresh-token rotation and expiration for the Native client, store only in privileged extension context, and threat-model compromise before shipping. Do not embed secrets in the extension bundle.

Auth0 is the identity provider, not StreetMap’s authorization policy engine. The API must still map external identity to a local user and authorize ownership, account status, vote/report rules, and scopes. Public note GET routes remain anonymous; mutations require a validated API access token. Do not create a token-minting proxy or accept website cookies from extension calls.

## Session, credential, and account lifecycle

- Auth0 owns password verification, email verification, password reset, optional MFA and provider credential security. StreetMap stores no password hash. Database-connection verification/reset workflows are supported, but they require a working email provider. The built-in provider is documented only for basic testing (10 messages/minute, excess discarded, no reliability guarantee, no custom templates); production needs an external email provider and its own configuration/cost. Auth0 Free excludes email workflow customization, so verify the exact plan/template workflow and sender before launch.
- Use short-lived API access tokens (initial proposal 5–15 minutes, provider policy-dependent), narrow audience and scope; validate on every protected request. Provider revocation/introspection or a local account/session version must cover compromised sessions, suspension, and deletion. Do not claim immediate JWT revocation without a revocation mechanism.
- Website BFF session: opaque, high-entropy server-generated ID, server-side record and expiry, rotate on login/privilege changes, revoke on logout/security events. Never log tokens, authorization codes, session IDs, or sensitive query parameters.
- Account deletion must revoke provider grants, website sessions, and any extension refresh grants; current extension access tokens remain valid only until their short expiry unless an online revocation/version check is used. Retain or anonymize note authorship according to a documented retention policy. Current non-null unique email and `ON DELETE RESTRICT` FKs make physical user deletion impractical; see the location/lifecycle document.
- Changes to email or provider identity must be explicit and audited. Never merge accounts merely because display name or unverified email matches.

## Threat controls

| Threat | Required control |
| --- | --- |
| CSRF on website cookie requests | SameSite cookie, CSRF token on unsafe methods, validate exact `Origin`; never mutate through GET. |
| XSS / token theft | BFF keeps tokens server-side; HttpOnly cookie; contextual output encoding, React text rendering, strict CSP/no unsafe inline script, dependency review, no unsafe HTML. XSS still can act as the signed-in user. |
| Extension token exposure | Short token lifetime, `storage.session`, privileged extension context only, strict message schemas, never expose token to Maps content script or page, narrow `host_permissions` for StreetMap API only when API calls ship. |
| CORS confusion | CORS is not authorization. Prefer same-origin BFF. API bearer requests accept only required origins; no `*` with credentials. Extension host permission and server CORS are distinct controls. |
| Brute force / abuse | Provider controls for sign-in, verification, reset and MFA; API per-user and per-IP rate limits for token exchange and mutations, progressive throttling, alerting, bounded request bodies. Avoid account-existence leaks. |
| OAuth redirect/code injection | Exact registered redirect URIs; authorization code, state, nonce for OIDC, PKCE S256, one-use code; validate issuer/audience/signature/expiry/nonce. No implicit grant or wildcard redirect. |
| Token replay/revocation | TLS; short access-token expiry; provider revocation/introspection or local version/status check for sensitive operations; rotate/revoke sessions and grants on security events. |
| CSRF/XSS via extension | Extension auth begins only from a user gesture; strict callback origin validation; no remote executable code; do not treat messages from the page/content script as trusted identity. |

## Unresolved decisions before implementation

1. **Tenant and commercial gate:** decide whether to pay for multiple tenants or accept one shared tenant for development/production; the current Free tier lists only one included tenant. Approve data region, retention/export/deletion, external production email provider/cost, expected MAU tier, and plan before production setup.
2. **Extension callback/PKCE gate:** establish the stable Web Store extension ID and matching dev build key, register the exact generated Chromium callback on a Native client, and test user gesture, browser callback, state validation, PKCE S256 code exchange and the API-audience access token in a real MV3 build. Auth0/Chrome docs support the pieces, not StreetMap's exact combination or Auth0-side token CORS behavior.
3. **API gate:** call a protected Go test endpoint with the extension access token; verify signature/JWKS, exact issuer, exact API audience, expiry, algorithm and scopes, plus rejection of wrong issuer/audience and ID tokens. The current Go backend does not yet have Auth0 configuration or protected endpoints.
4. **Website gate:** implement/test the BFF code callback, ID-token validation, `(iss,sub)` resolution, server-managed session creation and logout/revocation. Confirm `streetmap.in` can serve the Go BFF same-origin (or design exact-origin proxy/CORS/CSRF controls if separate). Cookies must be `Secure`, `HttpOnly`, host-only, and never exposed to web JavaScript. No website session currently exists.
5. **Email gate:** using the actual planned sender/provider and tenant, test signup verification, resend/recovery, reset completion, expired/reused links, deliverability, limits, and generic non-enumerating responses. Auth0's basic built-in sender is not production suitable.
6. Session/access-token lifetimes, revocation latency, MFA requirements, and deleted-user retention/anonymization policy still need product decisions.
